# React Markdown editor

`@react-markdown-kit/editor` is a React Markdown editor with three modes: rich, source
and preview. Your application passes a Markdown string in and gets a Markdown string
back. Nothing asks you to store editor JSON.

```bash
npm install @react-markdown-kit/editor @react-markdown-kit/renderer
```

```tsx
'use client'

import { useState } from 'react'
import { MarkdownEditor } from '@react-markdown-kit/editor'
import '@react-markdown-kit/editor/styles.css'

export function Notes() {
  const [value, setValue] = useState('# Notes\n\nStart writing.')
  return <MarkdownEditor value={value} onChange={setValue} />
}
```

That is the whole integration. The editor below is that component, running on this page.
The pane underneath is the exact string `onChange` gives you.

## The three modes

```ts
type MarkdownEditorMode = 'rich' | 'source' | 'preview'
```

- **rich** edits the document visually. Marks, headings, lists, tables, links and images
  are real nodes, not text you have to escape.
- **source** is the Markdown itself, always available, always the real file.
- **preview** is read-only output rendered by `@react-markdown-kit/renderer`. There is no
  second renderer inside the editor, so the preview and your published page agree.

All three project the same document, so switching modes cannot lose what one surface
could not show. Control the mode with `mode` and `onModeChange`, or set a starting mode
with `defaultMode`.

## Markdown in, Markdown out

`value` is a Markdown string. `onChange` hands back a Markdown string. Your database
column does not change, your static files do not change, and every other Markdown tool
you use keeps working on the same content.

The dialect is a preset shared with the renderer, so the editor writes what your pages
read:

```tsx
import { defineMarkdownPreset, gfm } from '@react-markdown-kit/renderer'

const appMarkdown = defineMarkdownPreset({ extensions: [gfm()] })

<MarkdownEditor preset={appMarkdown} value={value} onChange={setValue} />
```

Without a preset the editor is CommonMark. With `gfm()` it edits tables, task lists,
strikethrough, autolinks and footnotes.
<Link to="/docs/renderer/presets">Presets</Link>

## The round trip, with the evidence

The risk with any rich editor is that opening a file and saving it rewrites parts of it
you never touched. This editor keeps the original source and the byte span of every
top-level block, then writes unchanged blocks back from those bytes instead of
re-serializing them.

## Toolbar

The default toolbar covers marks, block types, lists, links, images, thematic breaks,
undo, redo and the mode switch. Icons are inline SVG, so there is no icon package.

```tsx
<MarkdownEditor toolbar={false} value={value} onChange={setValue} />
```

```tsx
<MarkdownEditor
  value={value}
  onChange={setValue}
  toolbar={(items) =>
    items.map((item) => (
      <MyButton key={item.id} onClick={item.run} pressed={item.active} disabled={item.disabled}>
        {item.icon}
        {item.label}
      </MyButton>
    ))
  }
/>
```

Each item carries `id`, `label`, `icon`, `active`, `disabled`, `group` and `run()`.
Labels come from the `labels` prop, so the chrome can be localized without touching the
document.

## Headless

When the editor has to live inside your own layout, keep the engine and drop the chrome.

```tsx
const editor = useMarkdownEditor({ value, onChange })

<MarkdownEditorProvider editor={editor}>
  <MyToolbar />
  <MarkdownEditorContent aria-label="Notes" />
</MarkdownEditorProvider>
```

`editor.commands` holds every verb the default toolbar uses: `toggleMark`,
`setBlockType`, `toggleBulletList`, `insertLink`, `insertImage`, `insertMarkdown`,
`setMarkdown` and the rest. No Lexical type appears on the root entry, and a test asserts
that `src/index.ts` and `src/types.ts` import nothing from `lexical` or `@lexical/*`
(<Link href={blob('packages/editor/tests/styling.test.tsx')}>`packages/editor/tests/styling.test.tsx`</Link>).
The opt-in `@react-markdown-kit/editor/lexical` entry is the exception, for extension
authors.

There is a level below React as well, with no DOM at all:

```ts
import { createMarkdownBridge } from '@react-markdown-kit/editor'

const bridge = createMarkdownBridge({ preset: appMarkdown, headless: true })
bridge.load(source)
const out = bridge.getMarkdown()
```

That is the same pipeline the React editor runs, which is why the round trip can be
proved in a test rather than described in a README.

## Images

Your application owns storage. The editor owns the insertion, the pending state and the
cancellation.

```tsx
<MarkdownEditor
  documentKey={note.id}
  value={value}
  onChange={setValue}
  onUploadImage={async (file, { signal, documentKey }) => {
    const asset = await uploadToMyStorage(file, { signal, documentKey })
    return { src: asset.url, alt: file.name }
  }}
/>
```

`context.signal` aborts when the editor unmounts. A rejected promise inserts nothing. A
`blob:` URL is never written into a document, so a saved file cannot contain a link that
only worked in one tab. Images that already have a URL need no configuration at all:
`![alt](src)` is in the default dialect, and reference images keep their definitions.

## Styling and server rendering

The stylesheet is optional. The editor is fully functional with no stylesheet loaded and
a test asserts it; its chrome takes your class names through `classNames`.
<Link to="/docs/styling">The styling contract</Link>

The editor owns selection, undo history and keyboard handling, so it is a client
component and carries `"use client"`. The renderer is not, which is why they are separate
packages: a server-rendered page that only displays Markdown never pulls Lexical into its
bundle. <Link to="/docs/server-rendering">Server rendering</Link>
