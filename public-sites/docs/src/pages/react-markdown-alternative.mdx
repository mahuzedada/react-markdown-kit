# react-markdown alternative, with a codemod

`@react-markdown-kit/renderer` renders Markdown as React elements with the same prop
names and the same meanings as `react-markdown` 10. It is not a drop-in replacement.
Three things differ, and two of them can bite you silently, so this page lists the
evidence before it lists the reasons.

```bash
npm install @react-markdown-kit/renderer
```

```tsx
import Markdown from '@react-markdown-kit/renderer'

<Markdown>{content}</Markdown>
```

## What matches

`docs/COMPATIBILITY.md` is generated by the test run, so it cannot drift from the code.
Identical input goes through both packages and the normalized HTML is compared. Against
`react-markdown@10.1.0`: **39 comparisons across 11 props, 39 produce identical markup**
(<Link href={blob('tests/compatibility.test.tsx')}>`tests/compatibility.test.tsx`</Link>,

`javascript:` and `mailto:`. `skipHtml` has the same default, `false`, in both packages.

## The three differences

### `className` is ignored, not rejected

`react-markdown` 10 throws `Unexpected className prop, remove it`. This renderer has no
`className` prop either, but ignores it at runtime. TypeScript rejects it, so TypeScript
code fails at build time. JavaScript code that still passes `className` loses the wrapper
with no error. Wrap the component instead.

```diff
-<Markdown className="prose">{content}</Markdown>
+<div className="prose">
+  <Markdown>{content}</Markdown>
+</div>
```

### `MarkdownAsync` and `MarkdownHooks` do not exist

This renderer is synchronous. `react-markdown` 10 exports `MarkdownAsync` and
`MarkdownHooks` for plugins that do asynchronous work. There is no equivalent export
here, and an async remark or rehype plugin will not run. The codemod leaves those imports
alone and says why (<Link href={blob('tests/codemod.test.ts')}>codemod tests</Link>).

### A dialect plugin cannot apply to a precompiled document

`react-markdown` only ever takes a string, so every plugin runs at parse time. This
renderer also accepts a `MarkdownDocument` that was compiled earlier. A plugin that
changes the dialect, such as `remark-gfm`, cannot add tables to text that has already
been parsed. Tree-transforming plugins still run. Compile with the same extensions you
render with, or pass the string
(<Link to="/docs/renderer/compiling">compiling a document</Link>).

## The codemod

The renderer package ships two commands. Both run on your machine and send nothing
anywhere.

```bash
npx rmk-compare 'content/**/*.md' --gfm   # render your corpus through both, diff it
npx rmk-migrate 'src/**/*.tsx'            # report what would change
npx rmk-migrate 'src/**/*.tsx' --write    # apply it
```

`rmk-migrate` is a dry run by default and edits import statements only. It keeps your
alias and your quote style.

```diff
-import ReactMarkdown from "react-markdown"
+import ReactMarkdown from "@react-markdown-kit/renderer"
```

It refuses to guess. `MarkdownAsync`, `MarkdownHooks` and imports that reach into
`react-markdown/lib/*` are left untouched with an explanation, and `rehype-raw` used
without a sanitizer is flagged rather than carried across, because that pair executes
author HTML. Each of those refusals is a test in
<Link href={blob('tests/codemod.test.ts')}>`tests/codemod.test.ts`</Link>.

`rmk-compare` exits non-zero on a difference, so a pull request can gate on it
(<Link href={blob('tests/compare-runner.test.ts')}>`tests/compare-runner.test.ts`</Link>).

```text
3 document(s) compared
  matching   3 (100%)
  differing  0
```

## Benchmarks, including the regression

Server rendering with `renderToStaticMarkup`, both sides parsing GFM, median of the
printed iteration count after five warm-up calls. Reference machine: Apple M4 Max on
Node 24.17. Baseline is `react-markdown@10.1.0`. Ratios are kit divided by baseline, so
below 1.00 is faster. Reproduce with `pnpm bench`
(<Link href={blob('benchmarks/run.mjs')}>`benchmarks/run.mjs`</Link>,
<Link href={blob('benchmarks/README.md')}>method and results</Link>).

| Document | Kit median | Baseline median | Ratio |
| --- | ---: | ---: | ---: |
| 1 KB | 2.69 ms | 2.23 ms | **1.21x slower** |
| 10 KB | 16.22 ms | 16.25 ms | 1.00x |
| 100 KB | 206.96 ms | 233.36 ms | 0.89x |

**The 1 KB row is a regression against `react-markdown` and it is open.** It is fixed
per-render cost, not a scaling problem: building the unified processor and walking the
content policy happens once per render whatever the document size. The fix is to cache
the processor per resolved configuration. It is tracked in
<Link href={blob('benchmarks/README.md')}>`benchmarks/README.md`</Link> and not done.

Re-rendering a document that was compiled once is the path that is faster on any size.

| Path | 10 KB median |
| --- | ---: |
| From a source string | 16.80 ms |
| From a precompiled `MarkdownDocument` | 5.99 ms |

Parsing is roughly 80% of the work, and `compileMarkdown` does it once.

## When to stay on react-markdown

Stay if any of these apply. They are the honest cases, not a disclaimer.

- **You use `MarkdownAsync` or `MarkdownHooks`, or an async remark or rehype plugin.**
  There is no equivalent here.
- **Your smallest documents are on a hot path.** The 1 KB case is 1.21x slower and the
  fix is not shipped.
- **Every byte counts and you render CommonMark only.** `react-markdown` is
  {' '}{gzipDifference('kit-renderer', 'react-markdown')} smaller gzipped.
- **You pass `className` from JavaScript and cannot audit the call sites.** TypeScript
  catches it; JavaScript does not.
- **The setup works and nothing on this page is a problem you have.** A renderer swap
  is risk with no reward if the current one is fine.

## When to switch

- You want raw HTML rendered as text and unsafe URLs emptied with no plugin list
  (<Link href={blob('packages/renderer/tests/render.dom.test.tsx#L56')}>security tests</Link>,
  <Link to="/docs/security">security model</Link>).
- You stream Markdown from a model and need every prefix of the document to render
  without throwing and without rewriting what is already on screen. That is 59 tests in
  {' '}<Link href={blob('packages/renderer/tests/streaming.test.tsx')}>`streaming.test.tsx`</Link>.
- You render the same document more than once and want to parse it once
  (<Link to="/docs/renderer/compiling">precompiled documents</Link>).
- You want the editor, the Mermaid plugin, the slides plugin and the template plugin to
  read the same compiled document as the renderer
  (<Link to="/docs/extensions">extensions</Link>).
