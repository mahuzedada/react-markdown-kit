# React Markdown editor

`@react-markdown-kit/editor` is a React Markdown editor with three modes: rich, source
and preview. Your application passes a Markdown string in and gets a Markdown string
back, so you never have to store editor JSON.

```bash
npm install @react-markdown-kit/editor @react-markdown-kit/renderer
```

```tsx
'use client'

import { useState } from 'react'
import { MarkdownEditor } from '@react-markdown-kit/editor'
import '@react-markdown-kit/editor/styles.css'

export function Notes() {
  const [value, setValue] = useState('# Notes\n\nStart writing.')
  return <MarkdownEditor value={value} onChange={setValue} />
}
```

That's all the setup there is. The editor below is that component running on this page,
and the pane underneath shows the exact string `onChange` gives you.

## The three modes

```ts
type MarkdownEditorMode = 'rich' | 'source' | 'preview'
```

- **rich** edits the document visually. Marks, headings, lists, tables, links and images
  are actual nodes, so you don't have to escape anything.
- **source** shows the Markdown itself. It's always available and it's the real file.
- **preview** is read-only output rendered by `@react-markdown-kit/renderer`. The editor
  doesn't have a second renderer inside it, so the preview matches your published page.

All three are views of the same document, so switching modes won't drop something one
view couldn't display. Control the mode with `mode` and `onModeChange`, or set a starting
mode with `defaultMode`.

## Markdown in, Markdown out

`value` is a Markdown string and `onChange` hands back a Markdown string. Your database
column and static files stay as they are, and any other Markdown tools you use keep
working on the same content.

The dialect is a preset shared with the renderer, so the editor writes the same Markdown
your pages read:

```tsx
import { defineMarkdownPreset, gfm } from '@react-markdown-kit/renderer'

const appMarkdown = defineMarkdownPreset({ extensions: [gfm()] })

<MarkdownEditor preset={appMarkdown} value={value} onChange={setValue} />
```

Without a preset the editor uses CommonMark. With `gfm()` it can also edit tables, task
lists, strikethrough, autolinks and footnotes.
<Link to="/docs/renderer/presets">Presets</Link>

## The round trip, with the evidence

The usual problem with rich editors is that opening a file and saving it rewrites parts
you never touched. This editor keeps the original source and the byte span of every
top-level block, and writes unchanged blocks back from those bytes instead of
re-serializing them.

The corpus is
<Link href={blob('fixtures/editor-roundtrip/corruption.json')}>`fixtures/editor-roundtrip/corruption.json`</Link>,
which holds {cases} documents that a previous line-oriented editor damaged on save (written up in
<Link href={blob('docs/AUDIT.md')}>`docs/AUDIT.md`</Link>).

| Layer | What is asserted | Result | Test |
| --- | --- | --- | --- |
| Editor: open, switch modes, close | The bytes are identical | {cases} of {cases} | <Link href={blob('packages/editor/tests/roundtrip.test.ts')}>`packages/editor/tests/roundtrip.test.ts`</Link> |
| Editor, with GFM off | The bytes are identical | {cases} of {cases} | <Link href={blob('packages/editor/tests/roundtrip.test.ts')}>same file</Link> |
| Serializer: `documentToMarkdown(compileMarkdown(source))` | The meaning is unchanged | {cases} of {cases} | <Link href={blob('tests/roundtrip.test.ts')}>`tests/roundtrip.test.ts`</Link> |
| Serializer | Saving twice equals saving once | {cases} of {cases} | <Link href={blob('tests/roundtrip.test.ts')}>same file</Link> |
| Serializer | The bytes are identical | 14 of {cases} | <Link href={blob('tests/roundtrip.test.ts')}>same file</Link> |

The last row is on purpose. The serializer canonicalizes, so a setext heading becomes
ATX and a `~~~` fence becomes a backtick fence. The editor path doesn't do that, because
it never re-serializes a block you didn't edit.

## Toolbar

The default toolbar covers marks, block types, lists, links, images, thematic breaks,
undo, redo and the mode switch. Icons are inline SVG, so you don't need an icon package.

```tsx
<MarkdownEditor toolbar={false} value={value} onChange={setValue} />
```

```tsx
<MarkdownEditor
  value={value}
  onChange={setValue}
  toolbar={(items) =>
    items.map((item) => (
      <MyButton key={item.id} onClick={item.run} pressed={item.active} disabled={item.disabled}>
        {item.icon}
        {item.label}
      </MyButton>
    ))
  }
/>
```

Each item carries `id`, `label`, `icon`, `active`, `disabled`, `group` and `run()`.
Labels come from the `labels` prop, so you can localize the chrome without touching the
document.

## Headless

If the editor needs to fit inside your own layout, you can keep the engine and drop the
chrome.

```tsx
const editor = useMarkdownEditor({ value, onChange })

<MarkdownEditorProvider editor={editor}>
  <MyToolbar />
  <MarkdownEditorContent aria-label="Notes" />
</MarkdownEditorProvider>
```

`editor.commands` holds every verb the default toolbar uses: `toggleMark`,
`setBlockType`, `toggleBulletList`, `insertLink`, `insertImage`, `insertMarkdown`,
`setMarkdown` and so on. No Lexical types show up on the root entry, and a test asserts
that `src/index.ts` and `src/types.ts` don't import anything from `lexical` or `@lexical/*`
(<Link href={blob('packages/editor/tests/styling.test.tsx')}>`packages/editor/tests/styling.test.tsx`</Link>).
The one exception is the opt-in `@react-markdown-kit/editor/lexical` entry, which is
there for extension authors.

There's also a level below React that doesn't need a DOM at all:

```ts
import { createMarkdownBridge } from '@react-markdown-kit/editor'

const bridge = createMarkdownBridge({ preset: appMarkdown, headless: true })
bridge.load(source)
const out = bridge.getMarkdown()
```

It's the same pipeline the React editor runs, which is why the round trip can be checked
in a test instead of just described in a README.

## Images

Your application handles storage. The editor handles the insertion, the pending state
and cancellation.

```tsx
<MarkdownEditor
  documentKey={note.id}
  value={value}
  onChange={setValue}
  onUploadImage={async (file, { signal, documentKey }) => {
    const asset = await uploadToMyStorage(file, { signal, documentKey })
    return { src: asset.url, alt: file.name }
  }}
/>
```

`context.signal` aborts when the editor unmounts, and a rejected promise doesn't insert
anything. A `blob:` URL never gets written into a document, so a saved file can't end up
with a link that only worked in one tab. Images that already have a URL don't need any
configuration, since `![alt](src)` is in the default dialect and reference images keep
their definitions.

## Styling and server rendering

The stylesheet is optional. The editor works fine without it (there's a test for that),
and its chrome takes your class names through `classNames`.
<Link to="/docs/styling">The styling contract</Link>

The editor handles selection, undo history and keyboard input, so it's a client
component and carries `"use client"`. The renderer isn't, which is why they're separate
packages. A server-rendered page that only displays Markdown won't pull Lexical into its
bundle. <Link to="/docs/server-rendering">Server rendering</Link>
